# Аудит LoveScanner (love-scanner)

Дата: 2026-08-31. Метод: чтение кода, `npm run build`, локальный запуск (`npm run dev`) + Playwright (Chromium) на ширинах 320/375px, ручная проверка через `browser_evaluate`. Правки в проект не вносились.

---

## 1. Что за проект, стек, состояние

LoveScanner (бот `lovescan_ai_bot`) — Telegram Mini App для анализа совместимости по фото и переписке: пользователь загружает 1–3 фото или скриншоты чата, GPT-совместимая vision-модель (Gemini 2.5 Flash / Flash-Lite напрямую и через OpenRouter, плюс Qwen2.5-VL как второй фолбэк) выдаёт процент совместимости и текстовые разборы. Часть разборов платная (Telegram Stars, включая подписку), есть реферальная система, колесо дня, лидерборд и сезонные ивенты. Стек: Next.js 16.2.10 (App Router, Turbopack), React 19.2.4, TypeScript 5 (strict), Tailwind CSS 4, хранилище — Vercel KV с фолбэком на in-memory `Map` в деве (`lib/kv.ts`), часть роутов при этом обращается к `@upstash/redis` напрямую. Тестов нет вообще (`package.json` — только `dev`/`build`/`start`/`lint`). `npm run build` **проходит успешно** (Next 16.2.10, Turbopack, 6.6s компиляция + 4.5s тайпчек, 27 маршрутов сгенерировано) — сборка не падает, это не находка. Локальный запуск и ручное прохождение сценариев показали, что базовый экран рендерится и работает, но найден ряд серьёзных проблем с авторизацией отдельных API-роутов, один полностью неработающий фичер из-за опечатки в имени файла и один баг вёрстки, ломающий горизонтальный скролл всей страницы.

## 2. Критичное — сломано или опасно

### 2.1 Массовая незащищённость API: `userId` берётся из тела/query без проверки подписи Telegram

В большинстве роутов есть комментарии, прямо объясняющие, почему `userId` **нельзя** брать из тела запроса (см. `app/api/scan/route.ts:28-29`, `app/page.tsx:24-26`) — и всё же добрая половина эндпоинтов делает именно это. Это позволяет любому вызвать эти роуты от имени произвольного чужого Telegram ID.

- **`app/api/invite/complete/route.ts:9-32`** — самое серьёзное: `referrerId`/`newUserId` полностью берутся из тела, единственная защита — ключ идемпотентности `ref:credited:${newUserId}` (строка 15-17). Атакующий может слать `referrerId = свой ID`, а `newUserId` — каждый раз новый произвольный (несуществующий) ID, и раз в 3 вызова начислять себе `ref:credits` (строка 20-27) без единого реального приглашённого пользователя. Это неограниченная накрутка бесплатных платных разборов.
- **`app/api/invite/use-credit/route.ts:6-14`** и **`app/api/custom-credit/use/route.ts:12-19`** — оба явно названы мёртвыми и уязвимыми в комментарии другого файла (`app/api/scan/unlock/route.ts`, комментарий рядом с реализацией разблокировки: «эти POST-обработчики больше не нужны и их стоит удалить: они принимают userId из тела без проверки подписи, то есть позволяют сжечь чужие кредиты чужим запросом»). Прочитано и подтверждено: оба файла действительно принимают `userId` из тела без всякой проверки и списывают кредит (`ref:credits:${userId}` / `custom:free_credit:${userId}`) — то есть любой человек может обнулить чужой платный кредит одним POST-запросом.
- **`app/api/wheel/route.ts`** (GET/POST) и **`app/api/mood/route.ts`** (GET/POST) — `userId` из query/тела без проверки; можно раскрутить/испортить состояние колеса дня или настроения любого пользователя.
- **`app/api/register-user/route.ts:9`**, **`app/api/leaderboard/route.ts:10`** — те же два почти дословно дублирующихся файла: `userId`/`optIn`/`name` без проверки подписи, пишут в `user:${userId}:seen` и список подписчиков пуша от имени любого ID.
- **`app/api/history/route.ts:9`**, **`app/api/scan/list/route.ts:7`**, **`app/api/scan/result/route.ts:11`**, **`app/api/check-paid/route.ts:10`** — то же самое; `scan/list` дополнительно отдаёт **чужую историю разборов** (проценты, режим, 140-символьный сниппет текста ИИ-разбора) любому, кто знает/переберёт `userId`, а `scan/result` позволяет **переписать** сохранённый текст чужого платного разбора по известному `scanId`.
- **`app/api/invite/join/route.ts:6-33`** — `userId` и `result` для «партнёра» берутся из тела без проверки; можно присоединиться к чужой invite-сессии от произвольного имени.

Контраст: `app/api/scan/route.ts`, `app/api/scan/unlock/route.ts`, `app/api/stars/create/route.ts`, `app/api/subscription/status/route.ts` делают это правильно — берут пользователя через `authUserOrDev(req)` из подписанного `initData`. То есть паттерн защиты в проекте есть и работает, просто применён не везде.

### 2.2 «Похожие результаты» — фича полностью не работает из-за опечатки в имени роута

Клиент вызывает `/api/similar` (`app/page.tsx:603` и `app/page.tsx:713`), но файл роута лежит в `app/api/similiar/route.ts` (опечатка: «similiar» вместо «similar», подтверждено сборкой — в выводе `npm run build` маршрут значится как `/api/similiar`). Next.js роутит строго по пути файла, поэтому оба вызова всегда получают 404, ошибка молча проглатывается через `.catch(()=>{})` (page.tsx:603, 715). Кнопка «Что было у других с похожим %» никогда не покажет данные, и сама агрегирующая статистика (`POST /api/similar` после каждого скана) никогда не накапливается.

### 2.3 `history/route.ts` пишет несовместимый формат данных в тот же KV-ключ, что и `scan/route.ts`

`app/api/scan/route.ts:54` кладёт в список `history:${user.id}` **строку `scanId`**, и `app/api/scan/list/route.ts:10-11` читает этот список именно как список ID и подгружает `scan:${id}`. Но `app/api/history/route.ts:12` кладёт в **тот же ключ** `history:${userId}` целый объект `{id, percent, full, mode, ts}` (строка 11). Если этот роут вообще вызывается (он не используется из `app/page.tsx` — используется параллельный, правильный путь через `scan/route.ts`), он тихо портит список: `scan/list` попытается сделать `kvGet('scan:[object Object]')`, получит `null` и просто отфильтрует запись, то есть скан «потеряется» из истории без каких-либо ошибок.

### 2.4 Фолбэк «сервис перегружен» отдаётся и в платных разборах, хотя код это явно запрещает

`app/api/love/route.ts:485-494` — итоговый `catch` на случай, если все 5 попыток (Gemini×2, OpenRouter×3) провалились, возвращает заглушку `{percent:84, full:"Сервис перегружен..."}` со статусом 503. Комментарий рядом явно говорит, что это допустимо только для бесплатного тизера, а платные типы должны честно получать ошибку — но код не проверяет `type` вообще и отдаёт одну и ту же заглушку для всех, включая `deep/hidden/future/custom/conversation`. На клиенте `app/page.tsx:429-436` статус ответа не проверяется вообще для payload'а с текстом — единственная проверка это `if(!data.full)` (строка 431), а у заглушки `full` есть, поэтому клиент рендерит фейковый текст как настоящий платный разбор и даже сохраняет его через `POST /api/scan/result` (строка 435) как если бы это был реальный ответ модели. Итог: если все провайдеры одновременно недоступны, заплативший пользователь получает и сохраняет выдуманный контент вместо настоящего анализа — то, что комментарий в коде прямо называет недопустимым.

### 2.5 Cron ежедневной рассылки, скорее всего, всегда падает: несовпадение имени переменной окружения

`app/api/cron/daily-push/route.ts:23` читает `process.env.TELEGRAM_BOT_TOKEN`. Во всём остальном проекте (webhook, stars/create, `.env.local`) используется переменная `BOT_TOKEN` — `TELEGRAM_BOT_TOKEN` в `.env.local` не определена вообще. При отсутствии значения роут сразу падает в `if(!botToken) return NextResponse.json({error:"no TELEGRAM_BOT_TOKEN"},{status:500})` (строка 25). Оговорка: проверено только по `.env.local`; если на Vercel в продакшене отдельно заведена переменная с именно этим именем — бага нет, но это не следует из просмотренного кода и стоит перепроверить в настройках проекта на Vercel.

### 2.6 Незащищённый debug-роут оставлен в проде

`app/api/debug/auth/route.ts` (весь файл, 97 строк) сам себя описывает как «ВРЕМЕННЫЙ РОУТ. Удалить, когда оплата заработает» (строка соответствующего комментария в начале файла) и не требует авторизации. Он отдаёт длину `BOT_TOKEN`, извлечённый из токена числовой ID бота и детальную диагностику проверки HMAC-подписи — сам токен не палится, но это всё ещё лишняя диагностическая поверхность, доступная кому угодно, и признанная автором кода устаревшей. Компонент `app/debug-panel.tsx`, который её вызывает, в `app/page.tsx` не импортирован (проверено `grep` — совпадений нет), то есть сама панель в UI не включена, но роут остаётся доступным напрямую по URL.

### 2.7 Длинный текст без пробелов рвёт контейнер и ломает горизонтальный скролл всей страницы (подтверждено вживую)

Проверено инъекцией DOM-узла с классом `.ai-font` (тот же класс, что использует `AnswerBox`, `app/page.tsx:778-780`) и строкой из 200 символов без пробелов внутри контейнера шириной 280px: контент растянулся до 1414px и **`document.documentElement.scrollWidth` вырос с 355px до 1415px** — то есть вся страница получает горизонтальный скролл. Причина: `AnswerBox` использует `whiteSpace:"pre-wrap"` (page.tsx:779) без `overflowWrap`/`wordBreak`, а `.ai-font` в инлайновом `<style>` (page.tsx:857) тоже не задаёт перенос длинных слов. Дополнительно `app/globals.css:29-37` содержит комментарий о том, что `overflow-x:hidden` с body сняли намеренно (ломал вертикальный скролл на iOS) — то есть у страницы сейчас нет вообще никакой защитной сетки от горизонтального переполнения. Ответы модели обычно — обычный текст с пробелами, но пользовательский вопрос («Свой вопрос», page.tsx:1129) или единичный «слипшийся» токен в ответе модели (ссылка, хэштег) воспроизведёт баг.

### 2.8 React hydration-ошибка при каждой загрузке (подтверждено в консоли браузера)

При навигации на `/` в консоли выводится ошибка `A tree hydrated but some attributes of the server rendered HTML didn't match the client properties`, указывающая на несовпадение атрибута `style` тега `<html>` (`--tg-viewport-height`, `--tg-viewport-stable-height`). Причина — скрипт `https://telegram.org/js/telegram-web-app.js`, подключённый с `strategy="beforeInteractive"` (`app/layout.tsx:44-47`), успевает выставить инлайн-стили на `<html>` до того, как React сверит серверный и клиентский рендер. Функционально страница продолжает работать (React просто не патчит эти атрибуты), но это настоящая, воспроизводимая ошибка в консоли на каждой загрузке — именно то, что просила найти Фаза 3.

## 3. Важное — работает, но плохо

- **Нет тайм-аута на запросы к провайдерам ИИ.** `callGemini()`/`callOR()` в `app/api/love/route.ts` (~строки 80-137) используют обычный `fetch` без `AbortController`, единственная защита — общий лимит функции `export const maxDuration = 60` (строка объявления в начале файла). Если первый провайдер в цепочке зависает близко к 60 секундам, оставшиеся 4 фолбэка физически не успевают выполниться — цепочка ретраев существует на бумаге, но при зависании конкретного провайдера не отрабатывает.
- **Защита от prompt injection — только текстом промпта, без структурной изоляции.** Вопрос пользователя в режиме «Свой вопрос» подставляется в промпт как `Вопрос пользователя: "${question}"` (внутри `buildPrompt`, `app/api/love/route.ts`, ветка `custom`) — кавычки в вопросе пользователя не экранируются, то есть строка `"` в вопросе технически может преждевременно «закрыть» цитату внутри промпта. Единственная защита от смены темы/инструкций — словесные правила в самом промпте (`THIRD_PARTY_RULE` и запрет отвечать не по теме), программной санитизации нет.
- **`app/api/telegram/webhook/route.ts` — проверка секрета вебхука «отказывает» только если секрет задан.** Условие `if(WEBHOOK_SECRET){ ... }` не имеет `else`-ветки с отказом: если переменная `WEBHOOK_SECRET` когда-либо окажется незаданной (например, забыли завести на новом деплое), проверка подписи вебхука молча отключится вместо того, чтобы блокировать все запросы.
- **Двойной клик по кнопкам генерации платных разборов не блокируется.** Кнопка «Вскрыть письмо» / «Пересобрать с деталями» (`app/page.tsx:1105`) вызывает `generate("deep")`, но в отличие от соседних кнопок покупки (`disabled={waiting===...}`) у неё нет `disabled={busy.deep}` — быстрый двойной тап отправит два параллельных платных запроса к `/api/love`. Та же проблема у кнопки «Задать вопрос» (page.tsx:1130): `disabled={!customQuestion.trim()}` не учитывает `busy.custom`. (Кнопка «Спросить ещё», page.tsx:1139, это уже делает правильно — `disabled={!customQuestion.trim()||busy.custom}`, то есть паттерн защиты в проекте есть, просто применён не везде.)
- **Два параллельных клиента для одного и того же хранилища.** Большинство роутов используют абстракцию `lib/kv.ts` (с фолбэком на in-memory `Map`, когда переменные `KV_REST_API_*` не заданы — специально для локальной разработки без реального Redis). Но `app/api/check-paid/route.ts:4-7`, `app/api/invite/create/route.ts:4`, `app/api/invite/join/route.ts:4`, `app/api/invite/session/[id]/route.ts:4` создают собственный `Redis`-клиент напрямую (`new Redis({...})` / `Redis.fromEnv()`) без какого-либо фолбэка — эти конкретные роуты упадут при локальной разработке без настоящих переменных Upstash/Vercel KV, в отличие от всего остального проекта.
- **`app/api/register-user/route.ts` и `app/api/leaderboard/route.ts` — практически дублирующиеся файлы.** Оба реализуют регистрацию пользователя и переключение push-подписки (различие — `leaderboard` дополнительно сохраняет `name`); ничего специфичного для лидерборда во втором файле нет. Похоже на копипасту при рефакторинге, оставленную в обоих местах.
- **`app/api/invite/create/route.ts:6-8`** содержит незакрытый `TODO: замените на реальный APP_SHORT_NAME из BotFather (/myapps)` — короткое имя приложения захардкожено как `"app"`. Если это не совпадает с реально зарегистрированным в BotFather именем, диплинки приглашений (`t.me/lovescan_ai_bot/app?startapp=invite_...`) не будут открывать мини-апп.
- **Контраст текста, скорее всего, не проходит WCAG AA.** `C.ink35 = rgba(244,239,231,0.35)` (`app/page.tsx:13`) используется для всех «label»-подписей (`label` стиль, page.tsx:769) и множества второстепенных текстов на фоне `#0A0908`. Расчётный контраст смешанного цвета к фону — примерно 2.6:1, что ниже минимума WCAG AA (4.5:1 для обычного текста, 3:1 для крупного). Это оценка вручную по формуле альфа-смешивания, не инструментальный аудит, но разрыв с порогом достаточно большой, чтобы не быть на грани.
- **Минимальный размер кликабельной зоны на мобильном не соблюдён.** Замерено вживую на 375px через `getBoundingClientRect()`: 9 интерактивных элементов меньше 44×44px — иконки-кнопки в шапке (лидерборд/колесо/история/уведомления/звук, все 32×32, `IconBtn` в `app/page.tsx:788`), переключатель «По отдельности/Вместе» (180×37, page.tsx:950), кнопки цены разбора (65×38, page.tsx:1085). Кнопка удаления скриншота переписки (page.tsx:1216) — 22×22, ещё меньше.
- **Много нативных `alert()` для ошибок и статусов.** Например `app/page.tsx:505, 515, 521, 531, 553, 569, 576, 617` — блокирующий системный alert внутри Telegram WebView визуально выбивается из интерфейса и не поддаётся стилизации/локализации по месту.

## 4. Косметика — вёрстка, мелочи

- **`README.md`** — не тронут после `create-next-app`, ноль документации по проекту.
- **`test.json`** в корне проекта — забытый тестовый payload для OpenRouter (`{"model":"qwen/qwen2.5-vl-72b-instruct","messages":[{"role":"user","content":"hi"}]}`), к коду приложения отношения не имеет.
- **Размеры шрифта в целом дисциплинированы** — единая шкала `F = {xs:11, sm:12.5, md:14, lg:16, xl:21, xxl:27, hero:42}` (page.tsx:19), но есть россыпь разовых инлайновых значений вне шкалы: `9.5` (page.tsx:938, 1222, 1395), `40` (page.tsx:1013), плюс отдельные размеры в canvas-коде для шаринга картинки (`28`, `300`, `26`, `42`, `24` — page.tsx:735-744). Не критично, но это именно тот «запах», который просила проверить Фаза 4.
- **Оттенки одного и того же цвета плодятся через произвольные hex-alpha суффиксы.** Например, `${C.gold}` встречается минимум с 11 разными суффиксами прозрачности (`0d,14,18,1c,1f,44,55,66,77,88` и без суффикса) вместо небольшого фиксированного набора уровней прозрачности — тоже симптом, о котором просила Фаза 4, хотя визуально не выглядит хаотично благодаря общей цветовой палитре.
- **`app/debug-panel.tsx`** — мёртвый код: нигде не импортируется (см. п. 2.6), включается по инструкции в собственном комментарии («вставить `<DebugPanel/>`…»), то есть существует только как ручной инструмент отладки, оставленный в репозитории.
- Клавиатурная навигация и видимость фокуса — **работают**: `button:focus-visible{outline:2px solid gold}` задано глобально (page.tsx:854), никаких находок.
- Дёргание layout при загрузке — не обнаружено: полноэкранный слой фона зафиксирован (`position:fixed`, page.tsx:896), контент использует `min-height:100dvh`, скелетоны (`Skeleton`, page.tsx:781) занимают место под контент до его прихода.
